# Production deployment: Render and Cloudflare

The canonical public origin is **[https://lastseat.ing](https://lastseat.ing)**. Render runs one Docker web service and owns the persistent application volume. Cloudflare remains the authoritative DNS provider. The committed [`render.yaml`](../render.yaml) is the production baseline; dashboard changes should be reflected back into that file.

## Security and data boundaries

- `HOST_SESSION_SECRET` is generated by Render and must remain stable, secret, and server-side.
- `/data` is a persistent Render disk; `MATCHES_DIR=/data/matches` stores the canonical world, sessions, research, Compound state, receipts, and reward ledger.
- `PUBLIC_ORIGIN` is exactly `https://lastseat.ing`, with no path or trailing slash.
- Public model inference, entry fees, predictions, economy labs, machine-payment demos, and real-SOL payouts remain disabled.
- The application never requests a seed phrase or private key. A linked wallet is a public address only.
- Do not copy a development data directory into production. The startup bootstrap creates the canonical production state on an empty volume.

## Render service

Create a Blueprint from this repository's `render.yaml`. It defines:

- one Docker web service named `lastseat`;
- the `/api/health` readiness check;
- a generated 256-bit session secret;
- a 1 GB disk mounted at `/data`;
- the canonical domain and safe production feature flags.

The Starter service and its persistent disk are billable Render resources. Review the workspace's current price before approving creation. Render supplies `PORT`; do not set it manually. The server binds to `0.0.0.0` in production and the container startup script drops privileges to the `node` user after preparing the mounted directory.

Before directing public DNS, confirm the Render service reports a successful deploy and that its temporary HTTPS URL returns ready state from `/api/health`.

## Attach `lastseat.ing`

1. In the Render service, add the custom domain `lastseat.ing`. Render also offers the corresponding `www` redirect.
2. Copy the service's exact `*.onrender.com` hostname from the Render dashboard.
3. In Cloudflare DNS, remove conflicting root/`www` A, AAAA, or CNAME records. Render does not accept IPv6 ingress, so no AAAA record should remain for these hosts.
4. Add CNAME `@` and CNAME `www`, both targeting the Render hostname. Keep both **DNS only** while Render verifies ownership and issues certificates.
5. In Cloudflare SSL/TLS, use **Full** during Render's documented verification flow. Never use Flexible.
6. Return to Render and verify the custom domain. Wait until the certificate is issued and valid.
7. Verify `https://lastseat.ing` and `https://www.lastseat.ing` in a browser. The root is canonical; `www` should redirect.
8. Cloudflare proxying can be enabled after Render shows valid certificates. If enabled, move to **Full (strict)** and re-run the release checks.

## Release verification

Run the non-mutating checks first:

```bash
npm run docs:check
npm run lint
npm test
cargo test --manifest-path rust/Cargo.toml --locked
```

After the domain is live, run the bounded deployment verifier:

```bash
DEPLOYMENT_VERIFY_URL=https://lastseat.ing npm run verify:deployment
```

The verifier checks readiness, simulated-only economy mode, canonical agents, shared-world routes, anonymous session isolation, a small private experiment, persistence during the request sequence, and owner-only export access. It creates one small private test experiment; it does not enable payments or publish private data.

Then manually inspect:

- `/world` loads and shared movement/live game feeds update;
- `/arena`, `/compound`, and `/private-arena` load;
- a fresh private browser receives a different anonymous session;
- no economy lab or funded route is public;
- the Bazaar describes internal test credits separately from future payouts;
- Render health and deploy logs contain no secrets or private experiment payloads.

## Rollback and recovery

If a deploy fails health checks, Render keeps the prior healthy release. Roll back the service image from Render rather than editing production files in place. Preserve `/data`; do not delete or replace the volume to fix an application deploy.

If DNS or TLS fails, switch the Cloudflare records back to DNS-only and verify the Render certificate and CNAME targets. Do not bypass browser certificate warnings. Restore the last known-good DNS records if the hostname cannot be validated.

Before any storage migration, take a provider snapshot or backup and follow the repository recovery procedures. Movement frames are ephemeral, but canonical results, research, private experiments, receipts, and idempotency records are durable application data.
