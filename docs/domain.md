# Connect a domain to the public app

This guide assumes the [single-service Railway deployment](deployment.md) is already healthy at its temporary Railway HTTPS URL. Buy a domain from a registrar you trust, such as Cloudflare Registrar or Namecheap. The registrar is where you renew the name; Railway is where this app runs. Keep registrar login recovery and auto-renewal configured.

1. Choose `<MY-DOMAIN>` (for example, `example.com`) and purchase it at the registrar. Do not buy hosting or email merely to use the domain for this website.
2. In Railway, open the **main** service → **Settings → Networking → Public Networking → + Custom Domain**. Add `<MY-DOMAIN>`. Copy the exact routing target and verification TXT record Railway shows. Use those values, not sample values in a guide.
3. In the registrar's DNS panel, configure the **apex** (`<MY-DOMAIN>`). Railway currently uses a host-provided CNAME target and verification TXT record. At the apex, use your DNS provider's **flattened CNAME**, **ALIAS** or **ANAME** pointing to `<HOST-CNAME>`, plus the exact TXT record Railway supplies. If your registrar cannot do apex flattening/ALIAS, use DNS hosting that can, or make `www` canonical instead. Railway does not supply a stable `<HOST-IP>` for a normal A/AAAA record; do not invent one.
4. Add `www.<MY-DOMAIN>` as a second custom domain in Railway if you want both names. At DNS, create a `CNAME` for `www` pointing to Railway's `<HOST-CNAME>` and its own required verification TXT record if Railway presents one. Choose one canonical hostname; use the registrar or edge redirect for the other. The application's `PUBLIC_ORIGIN` must match the canonical hostname exactly.
5. DNS record meanings: **A** maps a name to an IPv4 `<HOST-IP>`; **AAAA** maps to an IPv6 address; **CNAME** aliases a non-apex name to `<HOST-CNAME>`; **ALIAS/ANAME/flattened CNAME** provide CNAME-like behavior at the apex. Use an A/AAAA record only if the hosting dashboard actually provides that address for this service.
6. Wait for Railway to verify the DNS and issue its TLS certificate. Propagation can take time. Check the Railway domain status and visit `https://<MY-DOMAIN>/api/health`; do not rely only on DNS lookup success. Railway requires both its routing and TXT verification records.
7. Set `PUBLIC_ORIGIN=https://<MY-DOMAIN>` in Railway Variables and redeploy. This is the application's production `APP_ORIGIN` equivalent. Do not add a path, slash, port or `http:`. Keep the Railway-provided domain configured while testing.
8. Open `https://<MY-DOMAIN>/world` and `https://<MY-DOMAIN>/arena` in a normal browser and on a phone. Walk, observe another visitor's presence, inspect a profile, watch Survival, RPS and Tic-Tac-Toe. The world and Arena feeds use **SSE over HTTPS**, so the browser uses ordinary HTTPS URLs; no separate WebSocket port or mixed-content URL is needed. Ensure any proxy/CDN does not buffer or terminate long-lived SSE streams prematurely.
9. Run `DEPLOYMENT_VERIFY_URL=https://<MY-DOMAIN> npm run verify:deployment` from a built checkout. Then repeat the Browser A/B private experiment and JSON download check described in [deployment.md](deployment.md). Verify the URL and certificate from another device, not just the deployment machine.

Record the domain, registrar, Railway project/service, canonical `PUBLIC_ORIGIN`, volume and deployed commit SHA in your private operations notes. Do not put the signing secret in those notes unless they are stored in a proper secret manager.

Railway's current [domain instructions](https://docs.railway.com/networking/domains/working-with-domains) provide the exact dashboard sequence and DNS record values for your service.
