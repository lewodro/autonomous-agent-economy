Game credits, mock tool credits and SOL base units are separate currencies. Setting `wallet_enabled` or a model name does not connect normal game credits to a wallet. Neither a winner animation nor an imported rule-valid replay authorizes a funded payout.

## Funded competition flow

1. `FundedMatchConfig` validates 2–20 participants, exact decimal SOL strings, reserves, supported payment mode, zero house fee and funding timeout. Prototype host entry cap is **0.05 SOL per participant**; starting balance cap is **2 SOL**. HTTP defaults are a 0.02 entry, 1 starting SOL, 0.005 reserve and 600-second deadline. These are prototype settings, not production permissions.
2. A stable economy run ID binds the initial history/version/configuration to a distinct session instance. Canonical operation IDs bind run, purpose, payer and payee. Reusing an ID with a changed amount or other intent fails.
3. Each participant pays exactly its required entry to the match escrow account. Receipts must match the recorded intent. All entries and the exact account balance must verify before escrow locks and the Rust host starts game turns.
4. Rust advances the authoritative game; adapters propose bounded game decisions. Participants cannot submit a proposed payout winner, receipt or completion signature through funded host commands.
5. The host replays the completed history and signs domain-separated completion claims: economy run, engine version, final history/state/event hashes, winner and completion time.
6. A sole winner receives **100% of the pot**. For four entries of 0.02, the pot/payout is 0.08; four entries of 0.05 produce 0.20. This is supported mock arithmetic, not proof those amounts were paid on a public network.
7. A verified finished draw refunds entries. Cancellation before start and funding failure have explicit policies. Cancellation of a running match or uncertain payout is denied. Partial refunds and uncertain operations must reconcile the original intent.
8. Host snapshots and rail journals persist public operation facts. The mock rail commits debit and receipt together; the local rail persists exact signed bytes/reference before broadcasting. Duplicate settlement and restart use recorded operations.

Source owners: `rust/src/economy/host*.rs`, `coordinator.rs`, `binding.rs`, `attestation.rs`, `settlement.rs`, `refund.rs`, `mock_escrow.rs`, `durable_rail.rs`, `local_rail.rs`; Node admission/scheduling lives in `service/funded-runtime.js`.

## Local-validator custody and transaction verification

The backend generates and holds participant, escrow, fee-sponsor and host-authority keys. `LocalDevSigner` uses OS randomness, fixed backend paths, exclusive key creation, private Unix file permissions and fsync. Signing keys do not implement serialization. Key files are ignored by git. This is **trusted backend custody**, not an on-chain escrow program and not user-controlled wallet authorization.

Transactions contain a restricted System Program transfer and an operation-ID memo. Two real Ed25519 signatures authorize the participant/escrow source and separate fee sponsor. Transfers are capped at 1 SOL, which accommodates the maximum 20-seat pot at the 0.05 entry cap. Fee sponsorship keeps network fees outside the game pot. The prototype rejects nonzero house fees; it has no house-fee recipient implementation.

The rail pins an isolated validator genesis and loopback endpoint. Known public-cluster genesis prefixes are rejected. It checks the submitted reference against the locally signed transaction, then reads signature status and the parsed transaction. Verification checks execution success, slot, source, recipient, amount, sponsor/source signer roles, System Program, memo, reference, and absence of extra or inner instructions. A missing execution result now fails verification.

The local validator helper can provision disposable accounts with local faucet funds. Public devnet faucets, public balances, local faucet funding and real-value deposits are different facts. This audit did not run a local validator: no `solana-test-validator` executable was found in the current tool PATH. The ignored chain test must be run against an explicitly pinned isolated validator before claiming verified end-to-end local network settlement for this revision.

## Findings fixed during this audit

| Finding | Effect before fix | Fix / regression evidence |
|---|---|---|
| Missing `meta.err` interpreted as successful local execution | Incomplete RPC data could pass the success check | Require explicit `null`; missing/null/empty metadata regressions |
| Legacy wallet confirmation accepted missing `err` | Incomplete confirmation could be called successful | Require explicit execution result; processed/missing/failed/confirmed status tests |
| Legacy wallet trusted returned submission signature | Confirmation could follow a different reference | Require the exact locally derived transaction signature |
| Local wallet accepted a public genesis pin except devnet | A loopback proxy to another public cluster could pass the legacy local check | Shared isolated-cluster validation rejects mainnet/testnet/devnet prefixes |
| Funded agent IDs could collide with custody accounts | Custom `fee-sponsor` identity could fail or confuse account roles | Reject reserved sponsor/authority/escrow identifiers during admission |
| Scheduler could leave `RefundPending` stuck | `expire` only handled funding deadlines | Retry the saved cancellation reason; restart and duplicate-retry regression |
| Old compiler/crypto/action releases | Migration and maintenance drift | Current stable dependencies, immutable action pins and weekly Dependabot checks |
| SHA-256 0.11 removed old hexadecimal formatting | Direct update broke compilation | Stable lowercase encoding preserves history/operation/journal formats; published SHA-256 vectors and replay tests |
| Funded CLI allocated profiles before checking seat count | Extremely large untrusted count could exhaust memory | Bound 2–20 before configuration/session/key creation; invalid/maximum-integer regression |
| JS Solana demo accepted incomplete RPC/simulation results | Missing execution evidence could be reported as successful funded simulation | Validate response version/ID/result and require explicit simulation/faucet execution result |

Concurrent repository development incorporated the refund recovery fix in commit `8bff0c5`; it remains covered by the Rust host regression. Focused `debug_017` and later commits contain this audit's remaining changes.

## Remaining risks and missing production capabilities

| Priority | Finding / constraint | What would prove it resolved |
|---|---|---|
| Launch blocker | No mainnet rail, production escrow program, independently audited custody or token settlement | Explicit custody design, implemented authorized rail/escrow and external review |
| Launch blocker | Funded HTTP commands are local prototype controls; no account authentication, per-match ownership, participant wallet consent or production rate limits | Authenticated admission/control tests and restricted spectator access |
| Launch blocker | Backend owns every local wallet and host authority | Restricted production signer, secret store, rotation, recovery and permission audit |
| Launch blocker | Seeded xorshift is reproducible, operator-controlled game randomness | Published adversarial fairness/randomness protocol and verification evidence |
| High for public networks | Single RPC trust and `confirmed` commitment | Finality/reorg policy, independent receipt checks and orphaned-payment handling |
| Availability | Expired signed local transaction has no safe replacement state machine | Persist last-valid block height; prove expiry/non-landing before replacement; test ambiguous sends and restart |
| Availability | Failed/on-chain-rejected local operations can remain pending without an operator terminal-resolution flow | Distinguish pending, failed and expired; journal authorized recovery without duplicate payment |
| Availability | Extra unsolicited escrow funds cause exact-pot validation to stop; loss of fee-sponsor funds can stop settlement | Explicit excess-funds policy and sponsor fee/reserve monitoring |
| Accounting | Local rail keeps network fees outside the pot but does not journal each confirmed transaction's actual `meta.fee` | Record actual fees and reconcile fee-sponsor expenditure separately from stakes/payouts |
| Availability / storage | Local append-only JSON revisions grow; no production compaction, quotas, replicated DB or backup recovery | Bounded retention that preserves audit history, tested backups and crash/concurrency recovery |
| Trust | Journal SHA-256 detects accidental corruption but is not an authenticated log or protection against a filesystem administrator | Access control, external immutable log/anchors and rollback detection |
| Coverage | Actual local-chain test is excluded from default CI | Dedicated pinned validator CI for entries/payouts/refunds, restart and ambiguous operations |
| Capability | Public devnet funded matches, SPL tokens, token-creator fee collection and external-agent wallet deposits are absent | Dedicated implemented rails/indexers with exact transaction proofs and tests |
| Capability | Legacy tournament points do not trigger the funded native payment rail | Explicit tournament prize custody/admission/settlement integration |

`PUBLIC_ORIGIN` is an origin allowlist, not authentication. Loopback binding and Host/Origin checks mitigate cross-origin/DNS-rebinding access; they do not authorize every local process or protect a publicly forwarded server. Keep funded controls restricted to the development environment until ownership/authentication exists.

The prototype must never resolve an ambiguous payment by choosing a new recipient, signing a fresh operation, or automatically refunding around an unknown payout. Preserve the journal and validator ledger; deleting them discards the evidence needed for recovery.

Rust minimum is declared as 1.89 because the journal uses standard-library file locking. CI tests current stable Rust, not every historic compiler. Node 22/24/26 remain the tested supported majors; use maintained patched releases. Native TypeScript 7 installs a platform-specific compiler package through the locked npm optional dependencies; do not install with `--omit=optional`.

There are no third-party Node runtime libraries or Solana SDK dependency. The Rust/JS demos construct restricted legacy Solana wire messages directly. That narrow format supports these demonstrations; it does not implement arbitrary versioned transactions, SPL assets, priority-fee strategies or production wallet infrastructure. Pixi/Phaser/GSAP research files describe alternatives, not installed dependencies. No renderer replacement is required merely to use newer package versions.

`npm audit` reported zero known vulnerabilities after migration. RustSec reported zero vulnerabilities/warnings across **37 locked dependencies**, advisory database commit `ef6173cbc5c50ec8166f9a5b28f07834144373ee` (1290 advisories). Those are dated advisory results, not proof all code is secure.

## Reproduce the checks

```sh
npm ci
npm test
npm run lint
npm audit --audit-level=low
cargo test --manifest-path rust/Cargo.toml --locked
cargo audit --file rust/Cargo.lock
cargo test --release --manifest-path rust/Cargo.toml --locked maximum_size_match_is_replayable_within_transport_limits -- --ignored
```

For isolated chain integration, install the official Agave local validator, start it with `npm run solana:local`, retain its ledger, pin the emitted `LOCAL_GENESIS_HASH`, then run:

```sh
cargo test --manifest-path rust/Cargo.toml --locked actual_local_transfer_verifies_chain_and_survives_rail_restart -- --ignored
npm run demo:funded-local -- --mode local --agents 4 --entry 0.02
```

Use a separate `ECONOMY_DIR` for audit experiments and keep it for reconciliation.
